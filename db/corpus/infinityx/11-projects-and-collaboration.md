# Project Management and Multi-Core Collaboration Guide

Owner: Core Facility Administration · Reviewed annually

## 1. When to use a project

Most work does not need one. A single user booking a single instrument against a single
account code is fully described by the booking itself.

A project earns its place when work spans people, cores or funding sources — when the
question "what has this piece of work cost so far, across everything?" has no answer
without one.

Typical cases: a study using imaging and genomics; a collaboration between two labs; work
funded from two sources that must be reported separately; anything with a named deliverable
and an end date that someone will be asked about.

## 2. What a project holds

| Element | Purpose |
|---|---|
| Members | Who may book and raise requests against it |
| Cores | Which cores the work touches |
| Account codes | Which codes it may be charged to, and in what split |
| Bookings and requests | Everything attributed to the project |
| Spend to date | The running total, per core and per code |
| Documents | Protocols and agreements attached to the work |

## 3. Creating one

A Group Leader creates the project, names it, nominates members and attaches the account
codes. Core administration confirms that each code is valid and that any external members
have the necessary agreements in place.

Members are added and removed by the Group Leader at any time. Removing a member stops
future attribution; it does not detach their past bookings, which stay with the project
because they are part of what it cost.

## 4. Cost splitting

Where a project is funded from more than one code, the split is declared as percentages
when the project is created and can be changed prospectively at any time.

The split applies from the moment it is set. The facility does not re-split charges already
raised, because the record of who agreed to what at the time no longer exists — and a
retrospective split is a request to rewrite a financial record that has already been
reported.

Where a specific charge should go wholly to one code rather than following the split, set
it on the booking or request at the time it is made.

## 5. Attribution

A user who is a member of a project selects it when making a booking or raising a request.
Selecting it attributes the work and applies the project's account codes and split.

Attribution is optional per booking. A member's unrelated work stays unattributed, which is
the correct behaviour — a project total inflated by everything its members happened to do
is worse than no total.

## 6. Visibility

Project members see the project's bookings, requests and spend. The Group Leader sees
everything including per-member breakdowns. Core staff see the parts that touch their own
core.

A project spanning two labs makes each lab's contribution visible to both Group Leaders.
This is stated at creation and is the point: a collaboration where neither side can see the
cost is a collaboration heading for an argument.

## 7. Working across cores

Each core schedules its own work. A project does not create a shared queue, and raising a
request in one core does not raise it in another.

What a project does give you is sequencing: reference the related request in each core, and
staff can see the dependency and plan around it. The most common failure in multi-core work
is the second core discovering only on the day that it is waiting for the first.

## 8. Closing a project

A project is closed by its Group Leader when the work ends. Closing stops new attribution
and freezes the totals. Everything remains visible and reportable.

A project with no activity for one year is flagged to its Group Leader, and closed if there
is no response within thirty days. Closure is reversible on request.

## 9. Reporting

Per project, the facility can produce: total spend by core and by account code, instrument
hours by instrument, service requests by status, sample counts by state, and the list of
members with their contribution.

This is the report to ask for at the end of a funded piece of work, and it is the reason to
create a project at the start of one rather than reconstructing it afterwards from twelve
months of individual bookings.
